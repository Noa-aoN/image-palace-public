# 実際に起きた問題と、どう直したか

**測った数字だけを書いています。** 推測で直した話は入れていません。
ここに並べたものは、ほとんどが「動いているつもりだったのに動いていなかった」類のものです。

---

## 1. 同じカードを2回押すと、2クレジット引かれていた

外部から「`retry` の受付に競合がある」という指摘が届き、コードを読んで検証したところ**本当だった**。

受付は「状態を見る」「クレジットを引く」「`pending` にする」が別々のトランザクションで、
**カードの行を誰も押さえていなかった**。同時に2本来ると、どちらも「出来上がっている」と
判定して、それぞれ引き落とし、画像生成も2回走る。

ジョブ側には重複防止が3段ある（出来上がっていたら飛ばす・同じ注文はキャッシュを使う・
正規化プロンプトの UNIQUE 制約）。しかし**作り直しでは3段とも外れる**。
作り直しは鍵に使い捨ての値を混ぜるので、UNIQUE 制約にも当たらない。
`users` 行のロックは「残高以上に引く」ことは止めるが、**残高が足りる2本は両方通る**
（それを固定した spec が先にあった）。

### 直し方

読む前に**実スレッド2本の spec で再現**した。

```
修正前: expected: 1, got: 2      （2本とも受理・2回引き落とし）
修正後: 1 example, 0 failures
```

受付を `Images::AcceptRegeneration` に切り出し、**行を押さえた中で状態を読み直す**形にした。
負けた側は読み直した状態が `pending` なので、**既にある判定がそのまま断る**（新しい分岐を足していない）。

### そのあと見つかった、自分の修正の穴

レビューで「生成中のカードを押すと、行が空くまで待つようになっている」と指摘された。
生成ジョブは供給側への問い合わせのあいだ、ずっと同じ行を握る。つまり**修正前なら即座に
断っていた要求が、数十秒ブロックする**ようになっていた。本番は `statement_timeout`（30秒）に
当たって 500 になり、その間 Puma の枠と DB 接続を1つずつ占める。

これも測った。

```
修正前（素のロック）: 5.16 秒待ってから、受理していた
いま（lock_timeout） : 0.3 秒で断る
```

- 状態だけ先に見る段を、ロックより前に置いた（断る要求で外部 API も叩かない）
- 受付の中は `lock_timeout = 300ms`。取れなければ「重なりました」と断る
- 300ms は PostgreSQL の `deadlock_timeout`（既定1秒）より短くしてある。
  逆の順で行を取る処理（users → items）と掴み合っても、**こちらが先に諦めて相手を通す**

同じ形の受付が**残り3か所**ある。別の PR で同じ型に寄せている途中。

## 2. 一覧が遅かった。遅さの正体は「往復の本数」だった

カード一覧（1ページ24枚）が数秒かかっていた。原因は N+1 で、
サムネイルの添付を `includes` に入れ忘れていたため、1枚ごとに
「サムネある？」「その実体は？」と2往復ずつ増えていた。**82本・約5.6秒**。

本番の DB は隣の部屋には無い。当時はアプリが東京、DB が ap-southeast-1 で、
**片道70ms**。本数がそのまま待ち時間になる。

### 直し方

- 必要な添付を定数（`Item::MEDIA_INCLUDES`）に固め、一覧はそれを通す
- **速さは測らない。問い合わせの本数を数える** spec を置いた。
  速さは環境で変わるが、本数は変わらない。「枚数を増やしても本数が増えない」を固定する
- 認証まわり（devise-token-auth のトークン更新）は数から外す。同じ操作でも揺れるので

## 3. アプリを DB の隣へ動かした（70.2ms が 2.4ms）

往復の本数を減らしても、1本あたりが遅ければ意味がない。
Neon に東京リージョンが無く、DB は ap-southeast-1 にあった。

**DB を動かすのではなく、アプリを DB の隣へ寄せた**（Fly の `nrt` から `sin` へ）。
DB 往復は 70.2ms から 2.4ms になった。利用者から見た距離は少し伸びるが、
1リクエストで DB を何度も叩くアプリでは、こちらのほうが効く。

## 4. 防御が効いているつもりで、半分しか効いていなかった

Active Storage + libvips 構成に、未認証でも到達しうる任意コード実行の脆弱性が公表された。
成立条件を全部満たしていたので、多層防御を入れた——`VIPS_BLOCK_UNTRUSTED=1` と
`Vips.block_untrusted(true)` の二重掛け、マジックバイトでの allowlist、出力の検証、レート制限。

その後、**本番と同じイメージで実測**したら、`block_untrusted` は PDF と HEIF を
止めていなかった。

| ローダ | 結果 |
|---|---|
| svgload / magickload / jxlload | ブロック済み |
| pdfload | **到達**（poppler がパースを開始） |
| heifload | **到達 → プロセスが abort** |
| tiffload / gifload | 到達 |

止めていたのはマジックバイトの allowlist **単独**で、層が1枚しかなかった。
文書に書いた「PDF も止まる」は誤りだったので、そう追記した。

### 直し方

- 使わないローダモジュールを **Docker イメージから削除**（遅延ロードなので事前指定が届かない）。
  apt install と同一レイヤで削除する（後段のレイヤでは `.so` がイメージに残る）
- 読み込みオペレーション全体をブロックし、PNG / JPEG / WebP の3つだけ戻す
- **spec で固定した。** しかも「拒否された」だけでなく**拒否の理由**まで見る。
  ローダ不在のときのエラーと区別しないと、防御が外れた環境でもテストが通ってしまう
- あわせて、CI に libvips が無く**画像系の spec 30 例が黙ってスキップされていた**のを直した
  （`REQUIRE_VIPS=1` のときはスキップせず落ちるようにした）

## 5. テストが、開発用のデータベースで走っていた

`docker compose` の環境変数（`RAILS_ENV` / `DATABASE_URL`）が `database.yml` の `test:` を
上書きしていて、RSpec が開発環境・開発 DB で走っていた。緑だったので誰も疑わなかった。

### 直し方

`rails_helper` で接続先を決め、**末尾が `_test` でない DB につながっていたら1件も走らせずに止める**。
気づける形にしないと同じことが起きる。

## 6. 画像の共有キャッシュは、ほとんど効いていなかった（0.9%）

「同じ単語は世界で1回しか生成しない」が原価設計の中核だった。
実際に数えたら、**344回中3回（0.9%）**だった。利用者が少ないうちは語が重ならない。

この数字は機能を諦める理由にしていた（「キャッシュが効かなくなるから」）。
測ったあとは、**その理由を使わないことにした**。いま失うものがほとんど無いと分かったので。

## 7. ジョブと Web を同居させて、API が定期的に無応答になった

`SOLID_QUEUE_IN_PUMA` で Web とジョブを同じプロセスに置いていた。
画像生成が詰まると Puma が応答しなくなり、ヘルスチェックが critical になる。
復旧はマシンの再起動。

`app` と `worker` を別プロセスに分けて解消した。
**重い保守処理も worker 側で回す**（app で回して本番 API を 503 にしたことがある）。

## 8. ブラウザとサーバーの間で、アップロードが全滅していた

画像アップロードが届かない。request spec は通る。手元の curl も通る。
原因は**フロント側**で、axios が既定の JSON として `FormData` を畳んでいた。

テストが通っていても、ブラウザから実際に送るところまでは確かめられていなかった。
以降、入口を足したときは**実機で1回通す**ことにしている。

## 9. CI の無料枠を、月 2,900 分超えた

実測 4,900 分/月（無料枠 2,000 分）。原因は、重いテストを PR ごとに2回回していたこと。

- rspec を2つに分けて同時に走らせ、直列 582 秒を 344 秒にした
- それでも足りないので、**PR では回さない**形にした（週1と手動は残す）
- 代わりに「手元で何を通したか」を PR 本文に必ず書く運用にした

**無料枠に収めるために品質を落とさない**ことを優先した。落とすのは回す頻度。

## 10. 監視は鳴った。足りなかったのは、鳴ってから手を付けるまでの時間

DB（Neon）が止まり、Rails が起動できず全 API が 503 になった。
通知は正常に届いていた。問題は、届いてから対応に着手するまでの時間だった。

個人開発では「気づく仕組み」より「気づいたあと何分で動けるか」が効く、という学び。
復旧手順を手順書にして、同じ事象なら迷わず同じ順で戻せるようにした。
